# Как здесь работать, если git видишь впервые

Это руководство для тех, кто с git и GitHub раньше не сталкивался. Оно не про git вообще —
таких текстов много, — а про то, что нужно именно в этом репозитории, и про грабли, которые
здесь разложены. Английский `CONTRIBUTING.md` рядом — свод соглашений для тех, кто уже
освоился; сюда возвращаться не придётся.

Если что-то не сходится с тем, что написано здесь, — пиши в чат, а не подгоняй под текст.
Документ врал уже не раз, и это чинится.

---

## Часть 1. Один раз на машину

### Что поставить

**git.**

- macOS: `git --version` в терминале. Если git не стоит, система сама предложит поставить
  Command Line Tools — согласись и подожди.
- Linux: `sudo apt install git` (Debian/Ubuntu) или `sudo dnf install git` (Fedora).

**uv** — то, чем в проекте ставится Python и все библиотеки. Не нужно ставить Python
отдельно: uv скачает нужную версию сам.

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
```

Закрой терминал и открой заново, чтобы команда `uv` нашлась.

**gh** — программа для работы с GitHub из терминала. Строго говоря, без неё можно, всё
то же есть на сайте. Но с ней короче, и я буду показывать оба способа.

- macOS: `brew install gh`
- Linux: [инструкция по установке](https://github.com/cli/cli#installation)

### Доступ к репозиторию

1. Заведи аккаунт на github.com, если его нет.
2. Скажи ник в чат — тебя добавят в репозиторий. Придёт письмо с приглашением, его надо
   принять, иначе доступа не будет.
3. Свяжи терминал с аккаунтом:

```bash
gh auth login
```

Выбирай `GitHub.com` → `HTTPS` → `Login with a web browser`. Он покажет код, откроет
браузер, ты подтвердишь. Это делается один раз: дальше git перестанет спрашивать пароль.

### Забрать проект

```bash
git clone https://github.com/doctawho42/CYPChallenge.git
cd CYPChallenge
make setup
```

`make setup` делает четыре вещи, и все нужны:

| | зачем |
|---|---|
| ставит окружение | точные версии библиотек, те же, что у остальных |
| подтягивает подмодуль | репозиторий организаторов с официальной метрикой |
| качает данные | пять CSV челленджа, ~7 МБ, в git их нет |
| включает хук | локальную защиту от случайной отправки в `main` |

Занимает несколько минут. Проверь, что всё встало:

```bash
uv run pytest
```

Должно быть `6 passed`. Если да — можно работать.

## Часть 2. Что такое git, в трёх абзацах

**Репозиторий** — это папка, у которой записана вся история. Не «последняя версия», а
каждое изменение с самого начала, с автором и объяснением. Ничего не теряется: любое
состояние можно достать обратно.

**Коммит** — сохранённое состояние всех файлов плюс сообщение, зачем ты это сделал.
Сообщение важнее, чем кажется: через месяц ты будешь читать его, а не свой код. Коммит —
это не «сохранить файл», а «зафиксировать законченную мысль».

**Ветка** — отдельная линия коммитов. Пока ты работаешь в своей ветке, остальные тебя не
видят и ты им не мешаешь. Когда работа готова, ветка вливается в общую линию — `main`.

**GitHub** — копия репозитория на сервере, через которую мы синхронизируемся. Твой
компьютер и GitHub — два независимых хранилища; `push` отправляет туда, `pull` забирает
оттуда. Они не синхронизируются сами.

## Часть 3. Рабочий цикл

Одно и то же каждый раз. Выучи эти шесть команд — на девяносто процентов работы их хватит.

```bash
# 1. Забрать чужое, чтобы не работать на устаревшем
git switch main
git pull

# 2. Начать свою линию. Имя — латиницей, через дефис, по сути задачи
git switch -c seva/docking-descriptors

# 3. ... работаешь: правишь файлы, запускаешь скрипты ...

# 4. Посмотреть, что изменилось
git status
git diff

# 5. Сохранить
git add -A
git commit -m "докинг: расстояние и угол до Asp301 как признаки"

# 6. Отправить на GitHub
git push -u origin seva/docking-descriptors
```

После шестого шага git напечатает ссылку. Открой её — там будет кнопка **Compare & pull
request**. Нажми, напиши, что сделал и зачем, создай.

То же самое из терминала:

```bash
gh pr create --fill
```

Дальше внизу страницы PR появится проверка `split-guard`. Она идёт полторы минуты. Когда
позеленеет — жми **Squash and merge**. Или `gh pr merge --squash --delete-branch`.

Всё. Следующая задача начинается снова с пункта 1.

### Что такое pull request и зачем он

PR — это предложение влить твою ветку в общую. Он даёт две вещи. Во-первых, автоматические
проверки успевают отработать до того, как изменение попадёт к остальным. Во-вторых,
остальные видят, что ты сделал, и могут возразить до, а не после.

В проекте, где продукт — документ с числами, второе важнее первого.

## Часть 4. Грабли, разложенные именно здесь

### «pre-push refused» — так и задумано

Попробуешь отправить прямо в `main` — получишь отказ:

```
pre-push refused: main is updated through a pull request.
```

Это не поломка. `main` — то, на что ссылается документ, и он меняется только через PR.
Заведи ветку (`git switch -c имя`) и отправь её.

Заметь: `git switch -c` при уже сделанных коммитах их **не потеряет** — они переедут
в новую ветку вместе с тобой.

### Данные в git не лежат

После `git clone` в `data/` почти пусто, и это правильно. CSV челленджа качает
`data/fetch.sh` (входит в `make setup`), признаки строит `src/feats.py`. Они не в
репозитории, потому что и так доступны, а места занимают.

Поэтому же `git status` не показывает `data/feats.npz` — он в `.gitignore`. Файл есть,
git его просто игнорирует.

### Подмодуль — отдельная папка со своей историей

`CYP-Challenge-Tutorial/` — репозиторий организаторов, вложенный в наш. Если забыть
`git submodule update --init`, папка будет пустой и половина скриптов упадёт с жалобой на
`evaluation`. Лечится той же командой в любой момент.

### `results/preds/oof.json` руками не трогать

Это 750 КБ в одну строку, час счёта. Если git скажет, что в нём конфликт, **не пытайся
его разрешить** — там нечего разрешать глазами. Возьми одну из сторон и, если нужно,
пересчитай:

```bash
git checkout --theirs results/preds/oof.json   # взять версию с GitHub
git add results/preds/oof.json
```

И напиши в чат, что взял. Правило: перегенерирует этот файл кто-то один и предупреждает.

### Если `uv run pytest` покраснел — не правь тест

Там записан отпечаток разбиения на фолды. Он красный означает, что разбиение сдвинулось, и
все числа документа теперь описывают другие фолды. Чинить надо код, который его сдвинул.

Подгонка отпечатка под новый результат — худшее, что можно здесь сделать: проверка
замолчит, а числа разъедутся молча.

## Часть 5. Если что-то пошло не так

Почти всё в git обратимо. Ниже — рецепты на случаи, которые случаются со всеми.

**Наменял в файле и хочу вернуть как было** (до коммита):

```bash
git restore имя_файла        # один файл
git restore .                # все
```

**Сделал коммит, но передумал** (коммит ещё не отправлен):

```bash
git reset --soft HEAD~1      # откатить коммит, правки оставить
```

**Случайно закоммитил в `main`** — хук ловит только отправку, но не коммит:

```bash
git switch -c моя-ветка      # коммиты переезжают сюда
git switch main
git reset --hard origin/main # main возвращается к состоянию с GitHub
git switch моя-ветка
```

**git говорит, что ветки разошлись** — кто-то отправил своё, пока ты работал:

```bash
git pull --rebase
```

Твои коммиты переставятся поверх чужих. Если возникнет конфликт, git напишет, в каких
файлах; открой их, там будут отметки `<<<<<<<` и `>>>>>>>`, оставь нужное, убери отметки,
потом `git add файл && git rebase --continue`.

**Совсем запутался.** Ничего не потеряно. Напиши в чат, что делал, и покажи вывод:

```bash
git status
git log --oneline -5
```

По этим двум командам состояние восстанавливается однозначно. Не пытайся «почистить»
удалением папки — почти наверняка это лишнее.

**Чего не делать никогда:** `git push --force` в `main`, правка отпечатка в
`tests/test_split.py`, подъём потолка версий в `pyproject.toml` мимоходом. Каждое тихо
рассогласует числа с документом.

## Часть 6. С чего начать по существу

### Севе

Твоя линия — структурная. Ориентиры в коде:

- `src/feats.py` — где строятся признаки. Механистический блок (30 чисел) собирается
  функцией `mech_block`, там же видно, как признак попадает в матрицу.
- `data/mech_names.csv` — их имена по порядку.
- Фармакофор CYP2D6 сейчас представлен **бинарным флагом** `pharm_2d6`: катион в 2–5
  связях от арила. Сигнал в нём реальный — 54% активных против 29%, — но это флаг, а не
  геометрия. Замена на расстояние и угол до Asp301/Glu216 и есть задача.

Проверять эффект: `uv run python src/ablate.py` (час) и потом `src/score.py`. Критерий
объявлен заранее — эффект меньше 0.016 по макро ST-RAE на четырёх сидах считается
отсутствующим.

### Никите

Твоя линия — химическая.

- `src/pka.py` — правило оценки pKa самого основного центра. Оно писалось без химика,
  и `verify/f11_pka.py` уже намерил, что у 55.8% выборки ответ опирается на ароматический
  азот, а 2.2% попадают в конфигурацию, на которой правило провалилось на кофеине.
- `src/feats.py`, словарь `SMARTS` в начале — 16 структурных запросов. Какие из них
  осмысленны, а какие шум, никто не смотрел.
- TDI-трек: `src/tdibase.py` и `src/tdiprob.py`, пока только базовые линии. Механизм-зависимое
  ингибирование — это структурные алерты (фураны, ацетилены, метилендиоксифенил, тиофены,
  хиноны), и их там нет.

Менять SMARTS-строки можно прямо в `src/feats.py`, дальше `uv run python src/feats.py`
пересоберёт признаки за 45 секунд.

## Часть 7. Культура, которая тут есть

Три вещи, которые в этом проекте значат больше обычного.

**Отрицательный результат — результат.** Их в репозитории уже четыре, и они экономят
недели. Если проверил идею и она не работает — это надо записать, а не тихо бросить.

**Разность без интервала — не результат.** Смена сида разбиения двигает макро ST-RAE на
0.016, что больше типичного измеряемого эффекта. Любое «стало лучше» проверяется парным
бутстрапом и минимум четырьмя сидами.

**Числа проверяются пересчётом, а не доверием.** За одну ревизию в документе нашлось
двадцать одно расхождение, и пять скриптов оказались такими, что вообще никогда не
запускались. Если число выглядит странно — пересчитай его. Это здесь нормальная реакция,
а не придирка.
